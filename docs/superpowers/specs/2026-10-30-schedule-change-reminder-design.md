# 课表变更提醒 — 设计文档

- 日期：2026-10-30
- 版本：v1.2.0（versionCode 21，M6）
- 状态：已实现（v1.2.0 / versionCode 21，后续随 v1.2.1 修复）

## 0. 摘要

在现有只读教务 App 上增加「课表变更提醒」：每次拿到实时课表时，与前一次课表对比，识别**停课、调课、新增（补课）**三类变化，通过系统通知、首页提醒条、课表标记、桌面小组件角标和变更历史列表告知用户。检查时机为「打开 App 时」+「每天 07:10 / 12:50 后台各一次」。

判定只覆盖**本周生效**的课；换教室不提醒但进历史；下学期 / 下周才生效的变化不看不记。

## 1. 背景与目标

用户场景（三条同时成立）：

1. **课前预警**：怕白跑——课被停、被调到别的时间，希望课前知道。
2. **打开可见**：打开 App 就能看到「这周课表哪里变了」。
3. **留档备查**：保留一份变更记录，事能回查。

项目现状约束：

- Capacitor + Vue 3，Android 原生壳；数据层只读，仅 GET / 查询类 POST。
- 无后端、无推送服务，变更只能在本机计算。
- 登录 Cookie 由原生 `AuthCookieStore` 加密保存，后台任务可复用。
- 已有课表快照（`lzpu.zf.snapshot.v1`）与桌面小组件（1 个 00:05 重算闹钟）。
- 现有单测：JS 84 项（vitest）、Android 15 项（JUnit），必须保持全绿。

## 2. 范围与非目标

**范围内**

- 停课 / 调课 / 新增三类变更的识别与提醒
- 换教室的静默记录
- 前台对账、后台两次对账、通知、首页提醒条、Tab 红点、课表标记、变更历史页、设置开关
- 4x4 与 4x2 桌面组件「有变」提示

**非目标（本次不做）**

- 下周 / 未来周的变化提醒
- 考试、成绩、通知等其他数据的变更提醒
- 服务端推送、账号同步、多设备同步
- 每日检查时间的用户自定义
- 变更原因（停课理由）的解析——接口没有该字段，文案只陈述事实
- 选课 / 退课 / 评教等写操作

## 3. 已确认的产品决策

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 核心场景 | 课前预警 + 打开可见 + 历史备查，三者都要 |
| 2 | 变更来源 | 只对比课表接口（kbList），不解析通知文本 |
| 3 | 判定口径 | 停课 / 调课 / 新增提醒；换教室不提醒、进历史；教师、课程名、学分变化不记 |
| 4 | 时间范围 | 只看「周次包含当前周」的课；纯下周变化不提醒、不记录 |
| 5 | 检查时机 | 打开/切回 App 自动对账 + 每天 07:10、12:50 后台各一次 |
| 6 | 触达方式 | 系统通知 + 首页提醒条/红点 + 课表标记 + 组件角标 + 设置开关（默认开启） |
| 7 | 历史保留 | 30 天（同时最多 200 条） |
| 8 | 通知形式 | 一处变更一条通知，单次最多 5 条；点开进变更列表页 |
| 9 | 已读规则 | 看过即已读，「当天不再重复」通过对变更条目去重实现 |
| 10 | 后台失败 | 登录失效当天提醒一次；网络/接口失败静默 |
| 11 | 课表标记 | 角标 + 停课虚框：停课灰虚框「停」、调课橙「调」、新增绿「新」 |
| 12 | 架构 | 原生变更引擎，前后台共用一套解析与判定 |
| 13 | 前台通知抑制 | App 在前台时只写日志、由应用内提醒条展示，不发系统通知 |
| 14 | 换账号 | 基线与日志按学号归属；学号变化时重置基线并清空旧日志，不产生跨账号误报 |

## 4. 变更判定规则

### 4.1 会话规范化

一节「会话」由以下字段构成，其中**教室不参与判定**：

```
courseId + weekday + startSection + endSection + weeksSignature
```

- `courseId` = `kch`，缺失时退回 `kcmc`；课程名缺失的条目直接丢弃（与现有 `mapSchedule` 一致）。
- `weekday` = `xqj`，缺省 1。
- `startSection/endSection` = 解析 `jcs`（其次 `jc`），规则复刻 `parseSections`。
- `weeks` = 解析 `zcd`，规则复刻 `parseWeeks`（含区间、单双周、缺省 1–16 周）。
- `room` = `cdmc` 去掉「(80人)」这类人数标注后 trim，规则复刻 `cleanRoom`。
- `weeksSignature` = 周次升序后以逗号连接，用于比较与配对。

> 解析器必须与 `src/api/zf.js` 的 `parseWeeks` / `parseSections` / `cleanRoom` / 去重键**逐字节一致**。实现时用同一份 JSON fixture 在 JS 与 Java 两侧断言相同的会话集合。
>
> 单双周过滤后可能得到空周次（如自相矛盾的 `2周(单)`）：按「周次未知」处理，不参与本周判定，**不要**兜底成 1–16 周，否则会与课表显示不一致。

### 4.2 分类矩阵

先在**全量会话**上分类，再按「本周」过滤（顺序不能反，否则「周次调整」会被误判成停课）：

| 新旧关系（同一课程内） | 判定 | 类型 | 提醒 | 历史 |
|---|---|---|---|---|
| 新课表有、旧课表无（该课程无对应会话） | 新增（补课/加课） | `add` | 是 | 记 |
| 旧课表有、新课表无 | 停课 | `cancel` | 是 | 记 |
| 周次相同，星期或节次改变 | 调课 | `move` | 是 | 记 |
| 星期、节次相同，仅周次改变 | 周次调整 | `move` | 是 | 记 |
| 星期/节次与周次同时改变，且同课程剩余项一对一配对 | 调课（改时间又改周次） | `move` | 是 | 记 |
| 仅教室改变（其余相同） | 换教室 | `room` | 否 | 记 |
| 教师 / 课程名 / 学分改变 | 元信息 | — | 否 | 不记 |

「本周生效」过滤规则：

- `add`：新会话的周次包含当前周才保留
- `cancel`：旧会话的周次包含当前周才保留
- `move`：旧或新会话任一包含当前周即保留
- `room`：同上，按旧会话判断

### 4.3 配对算法

1. 按 `courseId` 分组。
2. **完全相同键**（含周次）配对 → 视为未变化；若教室不同，生成一条 `room` 记录。
3. 同课程剩余项先按「相同周次签名」配对：
   - 配对代价 = `|weekdayOld - weekdayNew| * 10 + |startSectionOld - startSectionNew|`
   - 贪心取最小代价，一对一配对，生成 `move`。
4. 仍剩余的旧/新会话，同课程内按相同代价再配对一次（周次不同也允许）：
   - 两侧各剩 1 条时直接生成 `move`（改时间同时改周次）
   - 两侧各剩多条时，贪心一对一配对，剩余不再配对
5. 仍未配对的旧会话 → `cancel`；仍未配对的新会话 → `add`。
6. 同一课程新旧数量不一致时，多出来的部分按上述顺序落入 `cancel` / `add`，不重复配对。

### 4.4 本周与时间边界

- 当前周 = `floor((今天 - 学期 startDate) / 7) + 1`，钳制在 `[1, 20]`；`startDate` 之前一律按第 1 周。与 `currentWeekOf` 一致。
- `startDate` 来自 `utils/term.js` 的 `buildTerm`（第一学期 08-31，第二学期次年 02-23）。
- **已过时段判定**：把变更对应会话换算到本周具体日期与节次起止时间（节次时间表见 5.4）。本周日期以**当前周的起始日**（`startDate + (currentWeek-1)*7`）为锚，取该 7 天周块内下一个同名星期；不假设 `startDate` 一定是周一（2025-08-31 是周日、2027-02-23 是周二）。对应会话取法：`cancel` 用旧会话，`add` 用新会话，`move` 优先用新会话（新会话不在本周时用旧会话），`room` 用旧会话。若对应上课时间已经结束：
  - 写入历史，`quiet = true`
  - 不进入提醒条计数、不发通知
- 周日 23:59 之后算下一周，纯下周变化不会被记录。

### 4.5 基线生命周期

| 事件 | 处理 |
|---|---|
| 首次使用 / 重装 / 无基线 | 只写基线，不报变更 |
| 学期切换（xnm 或 xqm 变化） | 重置基线，不报变更 |
| 换账号（学号变化） | 重置基线并清空旧日志，不报变更 |
| 离线快照（`offline = true`） | 不上交、不对比 |
| 新解析结果为空且旧基线非空 | 判定为接口异常，跳过本轮，保留旧基线（防「全部停课」误报） |
| 新解析抛错 | 跳过本轮，静默；debug 包记录原始响应摘要 |
| 同一轮多次触发 | 前台由 `academic.loadSchedule` 单飞合并并发请求；后台一次唤醒只跑一次 |

### 4.6 变更 id 与去重

- `id = 类型 + 课程 + 旧键 + 新键` 的 SHA-1 前 12 位，同一条变更多次检测得到相同 id。
- 通知按 id 去重：已发过的条目不再发第二次。
- 前台对账与后台对账共享同一份基线，因此同一条变更只会被首次检测生成一次。

## 5. 数据契约

### 5.1 基线（原生 SharedPreferences `lzpu_schedule_change`，键 `baseline`）

```json
{
  "term": { "xnm": "2025", "xqm": "3", "startDate": "2025-08-31" },
  "studentId": "2025XXXX0001",
  "sessions": [
    {
      "courseId": "B0001",
      "courseName": "高等数学",
      "weekday": 1,
      "startSection": 3,
      "endSection": 4,
      "weeks": [1, 2, 3],
      "room": "A101"
    }
  ],
  "sectionTimes": {
    "1": "08:20-09:00",
    "2": "09:05-09:45",
    "3": "10:05-10:45",
    "4": "10:50-11:30",
    "5": "11:35-12:15",
    "6": "14:30-15:10",
    "7": "15:15-15:55",
    "8": "16:15-16:55",
    "9": "17:00-17:40",
    "10": "19:30-20:10",
    "11": "20:15-20:55",
    "12": "21:00-21:40"
  },
  "savedAt": "2026-10-30T07:10:12+08:00"
}
```

- 每次实时拉取成功后整体覆盖。
- `sessions` 由原生解析原始 kbList 生成；JS 不上交已解析的会话，避免前后端解析差异。
- `sectionTimes` 由 JS 在调用时附带（取 `SECTION_TIMES`），原生并入基线。
- 同一 prefs 文件还保存：`entries`（变更日志）、`enabled`（开关）、`last_session_expired`（登录失效提示日期）。

### 5.2 变更日志（同一 prefs，键 `entries`）

```json
{
  "entries": [
    {
      "id": "c_9f3a1c2b7d10",
      "type": "cancel",
      "courseId": "B0001",
      "courseName": "高等数学",
      "from": {
        "weekday": 1, "startSection": 3, "endSection": 4,
        "room": "A101", "weeksLabel": "1-16周"
      },
      "to": null,
      "detectedAt": "2026-10-30T07:10:12+08:00",
      "detectedBy": "background",
      "quiet": false,
      "read": false,
      "notified": false
    }
  ]
}
```

- `type`：`cancel` | `move` | `add` | `room`
- `from` / `to`：变更前后会话快照；`add` 的 `from` 为 `null`，`cancel` 的 `to` 为 `null`
- `weeksLabel`：由原生压缩生成，连续周次用 `-`（如 `1-16周`），离散用 `,`，全单/全双追加 `(单)` / `(双)`
- `quiet`：对应上课时间已过，只作历史，不提醒
- `read`：已读标记
- `notified`：是否已发过系统通知
- 淘汰：超过 30 天或超过 200 条时按 `detectedAt` 从旧到新删除

### 5.3 设置（同一 prefs 文件）

| 键 | 类型 | 说明 |
|---|---|---|
| `enabled` | boolean | 课表变更提醒开关，默认 `true`；关闭后取消闹钟、清空通知栏，不删历史 |
| `notification_asked` | boolean | 是否已自动申请过通知权限，默认 `false`；只用于「首次对账后申请一次」 |
| `last_session_expired` | string | 登录失效提示去重日期（`yyyy-MM-dd`） |

- 通知权限**状态**不落盘，实时读系统；`notification_asked` 只记录「问过没有」
- 退出登录时清空 `baseline` 与 `entries`，保留 `enabled` / `notification_asked`

### 5.4 节次时间表

后台 Java 需要与 `src/utils/date.js` 的 `SECTION_TIMES` 一致。基线里附带 `sectionTimes`（由 JS 从 `SECTION_TIMES` 写入）；后台读取基线内的表，缺失时使用内置同值兜底：

```
1 08:20-09:00  2 09:05-09:45  3 10:05-10:45  4 10:50-11:30
5 11:35-12:15  6 14:30-15:10  7 15:15-15:55  8 16:15-16:55
9 17:00-17:40 10 19:30-20:10 11 20:15-20:55 12 21:00-21:40
```

## 6. 架构与流程

### 6.1 分层

```
Vue 页面 / store
      │  applySchedule(raw, term) / list / markAllRead / setEnabled
      ▼
ScheduleChangeBridge (Capacitor Plugin)
      │
      ├── ScheduleParser        kbList JSON → 规范化会话（纯函数）
      ├── ScheduleChangeEngine  旧会话 + 新会话 + 本周 + 当前时间 → 变更条目（纯函数）
      ├── ScheduleChangeStore   基线 / 日志 / 设置（SharedPreferences，加锁）
      ├── ScheduleChangeNotifier 通知渠道、权限、去重、深链、前台抑制
      └── ScheduleFetcher       OkHttp + AuthCookieStore → kbList 原文
              ▲
              │ 07:10 / 12:50 闹钟
      ScheduleCheckReceiver + ScheduleCheckScheduler
```

原则：**解析与判定只存在一份（Java）**；JS 只负责收集原始数据、调用原生、渲染结果。

### 6.2 前台流程

1. `academic.loadSchedule` 拉取成功，且 `offline` 为 `false`。
2. `api/zf.js` 在返回值中附带 `rawPayload`（原始 JSON）与 `term`（xnm / xqm / startDate）。
3. `stores/changes.js` 调用 `ScheduleChangeBridge.applySchedule({ raw, term })`。
4. 原生加锁执行：解析 → 与基线对比 → 写日志 → 更新基线 → 返回 `{ newEntries, unread, entries }`。
5. store 更新提醒条、Tab 红点、课表标记；页面从 store 读数。

失败（解析异常 / 桥调用失败）只记录，不影响课表显示。

### 6.3 后台流程

`ScheduleCheckReceiver`（AlarmManager `setAndAllowWhileIdle`）触发后：

1. 读设置、基线、加密 Cookie；任一缺失即退出（不报错）。
2. `ScheduleFetcher` 用 OkHttp GET `SCHEDULE_ENDPOINT`（同一学期参数，与 JS 相同的 `gnmkdm`），连接 4s / 读取 6s / 单次调用 8s，**只尝试一次**；重定向最多 5 跳但总时限 9s，保证不超过广播 `goAsync` 的 10 秒窗口；跳到 http 登录页才判会话失效，跨主机重定向按接口异常处理。失败静默，等下一时段。不放宽到前台 15s/20s。
3. 若被 302 到登录页或返回 401/403 → 判定会话失效：
   - 当天未提示过 → 发一条「登录已失效，点此重新登录」
   - 点击只打开 App，由路由守卫落到登录页
4. 解析 → 与基线对比（同一套引擎）→ 写日志 → 更新基线。
5. App 在后台：按 5 条上限逐条发通知；App 在前台：不发通知，触发 `changed` 事件让 JS 刷新提醒条。
6. 刷新 4x4 / 4x2 组件角标。

闹钟：每天两个单次闹钟（07:10、12:50），触发后各排下一天；`BOOT_COMPLETED` 时补排（新增独立 receiver，避免与小组件闹钟耦合）；App 启动时也补排一次（用户强停 App 会清掉闹钟，重新打开即恢复）。不使用精确闹钟，避免申请 `SCHEDULE_EXACT_ALARM`。

### 6.4 通知

- 渠道：`schedule_change`，名称「课表变更」，重要性 `DEFAULT`（声音跟随系统）
- 标题：`高等数学 · 已停课` / `高等数学 · 调课` / `高等数学 · 新增`
- 正文：`周一 3-4 节 · A101`（调课时 `原：周一 3-4 节 A101 → 新：周三 5-6 节 B203`）
- 每条通知独立 id（取变更 id 的 hash）；单次最多 5 条，超出的只进列表、不补发
- 点击：`Intent.ACTION_VIEW` + `lzpu://changes`，复用现有深链通道
- 权限：Android 13+ **首次成功对账后**申请一次 `POST_NOTIFICATIONS`（开关默认开，不能等用户手动开启）；拒绝或问过不再自动弹，设置页显示状态与跳转入口
- 去重：`notified` 标记；登录失效提示按日期去重

### 6.5 已读与未读

- 未读数 = `!read && isRemindable()` 的条目数（排除 `quiet` 与换教室），用于首页提醒条与 Tab 红点
- 进入变更列表页或点击提醒条 → `markAllRead` → 红点消失、提醒条隐藏
- 通知被点击 → 进列表 → 同样已读
- 历史页始终保留 30 天记录，不受已读影响

### 6.6 并发与前台抑制

- 基线 / 日志的读改写全部在 `ScheduleChangeStore` 的静态锁内完成
- 前台对账与后台对账互斥，后到的直接复用已更新的基线
- 后台拉取期间若前台已用更新的课表对过账，后台响应标记为过时并丢弃（比较基线 `savedAt`），避免反向变更
- 前台判定：`MainActivity.onStart/onStop` 维护静态可见标志；后台检查读该标志决定是否发通知

## 7. 界面设计

### 7.1 首页提醒条

位置：首页「今日课程」之后、「最新通知」之前。

```
┌────────────────────────────────────────┐
│ ⚠  本周课表有 2 处变更              ›  │
│    高等数学 · 周一 3-4 节 · 停课      │
└────────────────────────────────────────┘
```

- 仅在有未读且可提醒（非 `quiet`、非换教室）的条目时出现，否则整块不占位
- 副文案取 `detectedAt` 最新的一条
- 点击 → 标记已读 → 进 `/changes`

### 7.2 Tab 红点

- 底部 Tab「课表」图标右上角红点 + 数字（>9 显示 `9+`）
- 未读数归零即消失

### 7.3 变更列表页（`/changes`）

- 标题「课表变更」，返回按钮沿用 `BackBar`
- 筛选 chips：全部 / 停课 / 调课 / 新增 / 换教室
- 分组：今天 / 昨天 / 更早（按 `detectedAt` 本地日期）
- 卡片：
  - 类型彩色标签：停课红、调课橙、新增绿、换教室灰
  - 课程名
  - 停课：`周一 3-4 节 · A101`

  - 新增：`周三 5-6 节 · B203`

- 进入页面即 `markAllRead`

## 9. 异常与边界

| 场景 | 行为 |
|---|---|
| 接口返回空课表 / 解析失败 | 跳过本轮，保留旧基线，不产生变更 |
| 断网 | 前台显示「离线缓存」且不上交；后台静默 |
| 登录过期 | 当天一条提示，其余静默 |
| 通知权限被拒 | 不弹通知，提醒条与红点照常工作 |
| App 前台时闹钟触发 | 只写日志，不发通知，发 `changed` 事件刷新界面 |
| 学期切换 | 重置基线，首轮只建基线 |
| 跨周 | 周一 00:00 后按新周过滤；旧变更仍在历史 |
| 设备重启 | 开机补排两个闹钟，不清历史 |
| 退出登录 | 清空基线与历史、取消闹钟与通知、组件角标归零 |
| 用户强制停止 App | 闹钟被系统清除，需用户再次打开 App 恢复（写入设置页提示文案） |
| 教室名含全角括号人数标注 | 与 JS 保持一致，仅清洗 ASCII 括号（已知差异，列入已知限制） |
| 变更发生在周日、针对下一周 | 当天判定为「下周变化」不记录，基线已更新；跨周后不会补报（按决策 4 的有意行为） |
| 同一门课被拆成多条记录 | 按 4.3 贪心配对，不重复计数 |

## 12. 风险与已知限制

| 风险 | 影响 | 缓解 |
|---|---|---|
| kbList 周次/节次文本格式与假设不符 | 解析错位、误报 | 用真实响应 fixture 校准；解析失败跳过整轮；debug 包保留原始摘要 |
| Java 解析与 JS 显示解析不一致 | 课表显示与变更判定对不上 | 双端同一 fixture 断言；解析规则集中一份文档 |
| 逗号枚举周次（如 `1,3,5周`）沿用现有 JS 行为 | 可能只识别到最后一个单周 | 与现状保持一致，不在本次修正 |
| 国产 ROM 限制后台闹钟 | 提醒延迟或不来 | 设置页建议开启自启动 / 电池不优化；文档说明 |
| Doze 延迟 | 通知晚几分钟 | 使用 `setAndAllowWhileIdle`，接受偏差 |
| 用户强停 App | 闹钟失效 | 设置页提示「重新打开 App 恢复检查」 |
| 通知权限被拒 | 无系统通知 | 应用内提醒条 + 红点兜底 |
| 学校接口无「变更原因」 | 文案无法解释原因 | 只陈述事实，不推测 |
| 教室名人数标注若为全角括号 | 与 JS 一致地漏清洗 | 已知限制，后续统一 |
