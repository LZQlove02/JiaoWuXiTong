## 1. 执行摘要

### 1.1 总体结论

**建议保留现有总体架构，暂不允许真实账号接入；先修正网络安全实现契约、敏感 Cookie 存储方案和项目状态记录，再按受控流程验证真实登录。**

### 1.3 最高优先级风险

1.  **HTTPS-only 不能只靠把重定向 URL 的 `http` 字符串替换成 `https`。** 必须同时验证目标主机、端口、路径、重定向状态码、请求方法和请求体语义，并确保任何失败都不会回退到明文 HTTP。
2.  **`EncryptedSharedPreferences` 已被官方标记为 deprecated。** 应在接入真实会话前重新评估会话存储设计，不能只因旧实现可用就将其视为长期方案。
3.  **公开内容客户端与认证客户端必须有明确的网络安全边界。** 文档记录公开内容请求会跟随重定向，而真实登录设计要求手动控制重定向；若实现中共享不受约束的客户端，可能导致安全策略不一致。
4.  **当前 release 的功能定位必须写清楚。** 公开内容真实、教务数据模拟、真实登录未验收，三者不能混为一谈。
5.  **项目的"可复现构建"证据不足。** 使用本机缓存中的 Gradle 可完成本机构建，但另一台机器或 CI 能否构建，需要独立验证。

## 4. 架构与数据契约审查

### 4.1 架构判断

`Vue 3 + Vue Router + Pinia + AcademicApi + Mock/Zf 实现 + 原生网络插件` 的分层是合理的。它能避免页面直接依赖正方系统的字段名、HTML 结构和请求参数。

建议继续保留以下边界：

1.  页面只处理领域模型，不直接拼接正方接口 URL。
2.  `ZfAcademicApi` 负责教务系统的认证后数据。
3.  公开官网内容单独使用 `PublicContentApi`，不与需要登录的教务数据混在一起。
4.  原生网络层只负责受约束的 HTTP/TLS、Cookie、重定向和响应封装；业务解析放在适配层。
5.  Mock 和真实模式应显式标记，任何请求失败都不能静默回退为模拟数据。

### 4.2 统一接口存在遗漏

目前 `AcademicApi` 列出了通知列表，但没有明确列出通知详情、指南列表/详情和校历获取；这些功能却已经在公开内容模块实现。

**建议拆分接口：**

``` text
AcademicApi
  login / logout / getProfile
  getTerms / getSchedule / getGrades / getExams
  getEvaluations / submitEvaluation
  searchCourses / selectCourse / dropCourse

PublicContentApi
  getNotices(page)
  getNoticeDetail(id)
  getGuides(page)
  getGuideDetail(id)
  getCalendar()
```

实际方法名可以与现有源码保持一致。重点是把"公开网页数据"和"认证后的个人教务数据"作为两个不同的安全域。

### 4.3 HTML 解析稳定性

官网列表使用 CSS 选择器、详情正文使用 `.articleCon`，校历通过图片呈现。这种方式可用于个人客户端，但依赖网页 DOM 结构，容易受官网改版影响。

建议为每个解析器建立脱敏样本与单元测试，至少覆盖：

-   正常页面；
-   空列表；
-   登录页或错误页被误返回；
-   关键元素缺失；
-   正文没有 `<p>` 元素；
-   URL 为相对路径；
-   图片链接或详情链接变化；
-   编码或日期格式变化。

解析失败应与"真实空列表"严格区分。保留旧缓存、标注数据过期的策略是正确的。

### 4.4 数据模型待确认事项

-   `Session.weeks[]` 需要能表示单双周、临时调课和停补课。
-   `Grade.score` 不能只按数字处理，应支持缺考、缓考、重修、免修等状态。
-   GPA 与学分统计口径必须以学校网页端实际规则为准，不能自行套用通用公式。
-   学期起始日期、节次时间和考试起止时间应分开管理。
-   账号缓存键应使用稳定的学校用户标识，而不是姓名或展示名；切换账号时必须取消旧请求，并防止旧请求返回后覆盖新账号缓存。

## 5. Android / Capacitor 构建与兼容性审查

### 5.1 已有证据能支持什么

**\[文档记录\]** 方案记载 Capacitor 6、AGP 8.7.2、Gradle 8.14.4、JDK 17 的组合已经在本机完成构建，并在 Android 12、Android 16 设备上安装或验证了布局。

这能支持"该项目在记录的环境中可以构建运行"的结论，但不能自动证明：

-   干净环境可以重复构建；
-   所有依赖都可离线取得；
-   Android 8.0/API 26 运行正常；
-   未来 Android 版本不会改变系统栏或窗口行为；
-   本次报告已经独立复现上述结果。

### 5.2 Gradle 构建可复现性

文档说明由于本机没有 Gradle 发行 ZIP，直接调用本地缓存目录中的 `gradle.bat`，而不是依赖 Wrapper 下载。

这是一个可用的本机工作流，但不等同于仓库级可复现构建。其他开发者或 CI 可能没有同一缓存路径。

建议：

1.  在仓库中保留标准 Gradle Wrapper 文件，并固定 Gradle 版本。
2.  记录 Wrapper 分发地址及校验和。
3.  为无法直接访问官方分发源的环境，提供可审计的镜像或预下载流程，而不是依赖某台机器的缓存路径。
4.  在干净目录或 CI 上执行 `npm ci`、Web 构建、Capacitor 同步和 Android 构建。
5.  记录 Node、npm、JDK、AGP、Gradle、SDK、Build Tools 和锁文件版本。
6.  不把本机的绝对路径写成项目通用构建前提。

### 5.3 Android 最低版本与目标版本

-   `minSdkVersion = 22` 在数值上低于 Android 8.0/API 26，因此满足"最低支持版本不高于 API 26"的配置要求。
-   但它也意味着安装范围可能包含 Android 5.1 等更旧系统；若产品真正只承诺 Android 8.0 及以上，可以保留更低 minSdk，但必须说明兼容性测试范围。
-   文档承认 Android 8.0 未实机验证，这是准确的。建议把 API 26 模拟器或真机测试加入正式验收，而不是用 Android 16 设备代替。
-   目标 SDK 35 的 Android 15/16 系统栏适配已经有项目记录；但当前通过临时 opt-out 维持旧布局，不应成为未来版本的永久设计。

### 5.4 Edge-to-edge 的技术债

Android 官方文档说明：面向 Android 15/API 35 的应用在 Android 15 上会受到 edge-to-edge 强制行为影响；Android 16 的行为变更又说明，面向 API 36 及以上的应用不能继续依赖 `windowOptOutEdgeToEdgeEnforcement` 这一 opt-out。

因此，当前 targetSdk 35 下的布局处理可以作为过渡方案，但建议下一次目标 SDK 升级前，主动完成 Window Insets、安全区、状态栏/导航栏和横屏挖孔区域的适配。

**验收建议：** 将"当前 target 35 下布局通过"与"升级 target 36 前已完成 edge-to-edge 适配"分成两个不同的验收项。

## 6. HTTPS、TLS、重定向与登录安全审查

这是整个项目的最高风险区域。

### 6.1 现有安全判断的合理部分

方案已经明确：

-   不因证书错误而跳过 TLS 校验；
-   不为了登录成功而开放明文 HTTP；
-   CAS 证书过期时不使用真实凭据；
-   zfjw 直连 HTTPS 登录作为候选路径，必须通过受控验证；
-   不在验证期间执行选课、评教等写操作；
-   错误登录后若触发验证码，应停止自动重试。

这些安全边界应继续保留。

### 6.2 仅凭 HTTPS 登录页可访问，不足以判定全链路安全

必须分别验证：

1.  登录页 HTTPS 证书和主机名校验；
2.  登录 POST 实际目标；
3.  登录响应的状态码和 `Location`；
4.  认证后首页是否在 HTTPS 下建立；
5.  课表、考试、成绩等每个业务请求的协议；
6.  每个重定向的目标主机、端口和协议；
7.  Cookie 的 Domain、Path、Expires/Max-Age、Secure、HttpOnly 等属性；
8.  会话失效后是否返回登录 HTML 或重定向；
9.  失败时是否可能发生 HTTP 回退。

文档记载的 `zfjw` HTTPS 证书状态、CAS 证书过期、split DNS 和 HTTP 重定向是某一时间点的调查记录。本报告没有重新探测这些域名，因此这些项目必须在正式联调时再次确认。

### 6.3 "把 HTTP Location 改成 HTTPS"需要严格限制

**\[审查推断\]** 把重定向 URL 的 scheme 从 `http` 改为 `https`，只能作为一种受控重试策略，不能作为服务器支持 HTTPS 的充分证据。

实现必须满足：

-   先解析并规范化 URL，再校验 scheme、host、port 和路径。
-   只允许明确列出的主机名；拒绝未知主机、异常端口和非预期跳转。
-   禁止自动重定向，逐跳检查状态码和目标。
-   限制重定向次数，防止循环。
-   正确处理 301/302/303/307/308 对请求方法和请求体的语义差异。
-   登录密码、ticket、Cookie 不得转发到未经授权的目标。
-   scheme 改写后仍须验证证书和主机名。
-   重试失败后终止请求，不能回退到 HTTP。
-   对每个业务接口独立验证，不能仅凭首页成功就判定所有接口通过。

需要特别防范一个实现错误：重定向时无条件重复发送原始 POST 请求体。认证流程应根据真实状态码和服务器行为确定下一跳请求方法，不能简单地"原样重发"。

### 6.4 Android 的明文流量策略是纵深防御，不是唯一控制

Android 官方资料指出，Android 9/API 28 起，默认情况下明文流量支持会被关闭；网络安全配置可以进一步控制明文流量。但应用仍应在自己的网络层明确拒绝 `http://`，并对重定向目标进行校验。

建议同时实施：

-   Android Network Security Config 不允许明文流量；
-   认证网络层仅接受 HTTPS；
-   在每次请求前验证目标 URL；
-   禁止自动跟随未经验证的重定向；
-   测试过程中验证 HTTP 请求确实被阻止；
-   不设置 trust-all、忽略证书错误或自定义不安全的 TrustManager。

不要把"Android 默认禁止明文"当作可以省略应用层检查的理由。

### 6.5 公开内容与认证内容应使用不同的策略边界

文档记录公开内容插件会跟随重定向，而真实登录方案计划手动处理重定向。建议将其拆分为：

-   `PublicContentHttp`：访问有限的公开 HTTPS 主机，强制 HTTPS，限制重定向和请求频率。
-   `AuthenticatedJwxtHttp`：只用于真实教务认证与业务请求，持有 CookieJar，严格控制主机、协议、重定向和敏感日志。

底层代码可以复用，但认证 Cookie、会话状态、重定向策略与日志规则不能意外混用。`Access-Control-Allow-Origin: *` 不是安全证明，也不能证明接口不需要认证；CORS 是浏览器安全机制，不是原生 HTTP 客户端的身份认证机制。

### 6.6 受控登录测试的最低安全要求

在用户自行授权和输入凭据后，测试只应进行一次登录与必要的只读查询：

-   不由执行者代填或记录密码；
-   不把密码放在命令行参数、脚本输出或日志中；
-   不输出 Cookie、ticket、完整敏感 URL；
-   使用临时 Cookie 容器，测试后清理；
-   不执行选课、退课、评教等写操作；
-   只保留协议、状态码、跳转主机、接口结果类型等最小化证据；
-   任何必要请求只能通过 HTTP 才能完成时，立即判定安全准入失败。

## 7. Cookie、存储、缓存与隐私审查

### 7.1 `EncryptedSharedPreferences` 的弃用状态

**\[外部核验\]** AndroidX 官方 `EncryptedSharedPreferences` API 文档将该类标记为 deprecated（自 Security Crypto 1.1.0 起）。

这并不意味着现有实现必然立即失效，但意味着方案不应把它直接当作长期推荐的会话存储方案。建议在真实 Cookie 接入前重新评估：

-   是否能减少持久化会话的需求；
-   是否需要持久化 Cookie，还是每次启动重新登录更合适；
-   若必须持久化，如何用 Android Keystore 保护加密密钥；
-   使用的加密封装是否仍受维护；
-   密钥丢失、应用升级、数据迁移和异常恢复如何处理；
-   旧版存储如何迁移或清理。

不建议为了绕过弃用问题而随意自写密码学实现。应使用维护中的平台能力或经过审查的实现，并记录安全设计决策。

### 7.2 敏感 Cookie 不应进入 WebView 的 JavaScript 存储

建议：

-   CookieJar 和会话处理留在原生层；
-   Vue 页面不直接获取 Cookie、ticket 或密码；
-   `localStorage` 只存放主题、非敏感 UI 状态和经过评估的公开内容缓存；
-   个人成绩、课表等缓存放在应用私有存储中，并按用户和数据域隔离；
-   日志不包含密码、Cookie、ticket、姓名、学号或成绩正文。

文档中 4.1 的"`@capacitor/preferences` + localStorage：会话 Cookie、缓存、主题"与 5.3/6.1 的"Cookie 存 Android 加密存储、个人缓存放私有目录"并不完全一致。应统一为一张数据存储矩阵，明确每类数据的存储位置、加密方式、保留期限和清理时机。

### 7.3 退出、切换账号和并发请求

不能只清空缓存键。还必须防止旧账号的在途请求在切换后返回，并写入新账号的数据区。

建议实现统一的会话代次或取消机制：

1.  登出/切换账号时先使当前会话代次失效；
2.  取消旧账号所有可取消的请求；
3.  清理旧账号的 Cookie 和私有缓存；
4.  新账号登录成功后再加载数据；
5.  每个响应写入缓存前验证请求所属账号仍是当前账号；
6.  测试"旧请求晚于新登录返回"的竞争条件。

### 7.4 缓存清理范围需要写清楚

公开内容列表/详情存入 localStorage，校历图片则存为应用私有文件 `files/calendar.jpg`。文档明确写到清除缓存会清理公开内容条目，但没有足够明确地说明该按钮是否也删除校历图片文件及相关元数据。

建议列出清理范围：

  操作               应清理的内容
  ------------------ ------------------------------------------------
  清除公开内容缓存   通知、指南列表和详情缓存、校历图片及相关时间戳
  退出登录           当前账号会话与个人数据缓存；是否保留学号需明确
  切换账号           旧账号 Cookie、内存状态、在途请求和个人缓存
  清除全部缓存       所有可重建缓存，不应误删应用签名或不可恢复配置

`allowBackup=false` 是一项有用的控制，但不能仅凭一个 manifest 属性就宣称所有数据迁移或备份路径都已验证。应按照目标 Android 版本检查备份规则和设备迁移行为。

## 9. 发布、版本与维护审查

### 9.1 当前发布包应如何定位

文档记录了 `v1.0.3 / versionCode 4` 的签名 release。由于 release 默认 Mock，且真实登录未通过安全准入，这个版本适合描述为：

不要将"签名验证通过"与"业务功能完整"混为一谈。

### 9.2 签名密钥

加入 `.gitignore` 是必要措施，但不代表签名密钥已完成离线备份。建议：

-   私钥文件不提交仓库；
-   `keystore.properties` 不包含在仓库；
-   离线备份应加密并限制访问；
-   明确恢复流程，定期验证备份可用；
-   不将密钥放在普通云同步目录；
-   版本升级前验证包名、签名一致性和 versionCode 递增。

### 9.3 维护策略

公开官网页面结构、正方接口和服务器 TLS 配置都可能变化。建议保留：

-   接口/解析器版本记录；
-   脱敏样本与自动化测试；
-   失败率和解析错误类型统计（不记录敏感内容）；
-   明确的"暂不可用"提示；
-   用户可见的数据来源和抓取时间；
-   对官网请求的合理频率与缓存策略；
-   学校相关规定和公开内容使用范围的复核。

## 12. 建议的下一步执行顺序

1.  **先审代码，不先试真实账号。** 检查 `JwxtHttp`、OkHttp 配置、重定向处理、Network Security Config、CookieJar 和日志脱敏。
2.  **修订会话存储方案。** 处理 `EncryptedSharedPreferences` 的弃用问题，并明确 Cookie 的生命周期与清理规则。
3.  **把公开内容与认证网络分离。** 给两个客户端设置不同的允许主机、重定向策略与数据边界。
4.  **补齐自动化测试。** 先覆盖 HTTP 降级、未知主机重定向、证书异常、登录 HTML 误解析、账号切换竞争条件。
5.  **由用户授权后执行受控验证。** 不记录凭据，只执行登录与只读请求。
6.  **先开放只读核心功能。** 依次接入课表、考试，再处理成绩；所有数据与网页端比对。
7.  **最后处理写操作。** 选课、退课、评教必须有重复提交保护、超时后的服务器状态查询和明确的失败提示。
8.  **更新版本与验收文档。** 真实功能通过后，才将真实数据版本与当前 Mock 预览版区分发布。

## 13. 外部技术资料与交叉核验来源

以下资料用于核对通用 Android 安全与兼容性规则。访问日期统一记录为 **2026-10-27**。这些来源不验证学校服务器当前的 DNS、证书或实际响应；这些仍需由项目环境重新测量。

1.  **Android Developers --- Network security configuration**\
    https://developer.android.com/privacy-and-security/security-config\
    核验点：Android 网络安全配置、明文流量控制与 domain-config 的使用。官方资料指出，Android 9/API 28 起默认关闭明文流量支持；这支持"应用层 HTTPS-only + 平台配置纵深防御"的建议。

2.  **Android Developers --- Security with network protocols**\
    https://developer.android.com/privacy-and-security/security-ssl\
    核验点：TLS 与证书验证。用于支持不得忽略证书错误、不得使用 trust-all 校验器的安全要求。

3.  **Android Developers --- Cleartext communications**\
    https://developer.android.com/privacy-and-security/risks/cleartext-communications\
    核验点：明文通信风险与缓解方式。支持将任何必要 HTTP 请求视为真实账号接入的安全阻塞项。

4.  **AndroidX API Reference --- EncryptedSharedPreferences**\
    https://developer.android.com/reference/androidx/security/crypto/EncryptedSharedPreferences\
    核验点：官方 API 文档将 `EncryptedSharedPreferences` 标记为 deprecated。该事实意味着需要重新评估长期存储方案，但不等于当前项目已经发生存储漏洞。

5.  **Android Developers --- Behavior changes: Apps targeting Android 15 or higher**\
    https://developer.android.com/about/versions/15/behavior-changes-15\
    核验点：targetSdk 35 与 Android 15 的 edge-to-edge 行为。

6.  **Android Developers --- Behavior changes: Apps targeting Android 16 or higher**\
    https://developer.android.com/about/versions/16/behavior-changes-16\
    核验点：面向 API 36 及以上的应用不能继续依赖 `windowOptOutEdgeToEdgeEnforcement`；支持将当前 opt-out 方案视为有期限的兼容措施。

7.  **Android Developers --- Display content edge-to-edge in Views**\
    https://developer.android.com/develop/ui/views/layout/edge-to-edge\
    核验点：Window Insets 与 edge-to-edge 的正式适配方向。

8.  **Capacitor 6 Android 文档（后续复核入口）**\
    https://capacitorjs.com/docs/v6/android\
    用途：核对 Capacitor 6 对 Android 工程与平台配置的要求。**本报告未独立验证该文档中的每一项版本约束，也未由公开资料单独证明项目中的 AGP/Gradle/JDK 组合对所有环境均兼容；该组合目前只按用户文档记载为本机已构建。**
