## 1. 摘要

第二轮审查不再重复第一轮的结论，而是按"一条数据从产生到删除"的纵切方式检查跨模块链路。核心发现：

1. 未发现新的 P0。第一轮的证书固定与加密落盘修复仍然有效。
2. 真正的问题集中在**"用户以为关了其实没关、以为删了其实没删"**：
   - 通知/消息缓存（`portalCache`）退出登录后从不清理；
   - 附件与正文图缓存、本地崩溃摘要不在退出清理范围；
   - 退出登录不关闭「保持登录」，重新登录后被旧偏好自动恢复；
   - 子同意（后台检查、保持登录）版本升版后不会自动停用后台能力。
3. 三个高度可疑点经复核后排除：缺 `SCHEDULE_EXACT_ALARM`、CSS 全 px 字号、路由全量静态 import。
4. 另有两条技术项未在本轮修复：崩溃脱敏覆盖不足（P1）、通知 ID 同类碰撞（P2）。
5. 无障碍与依赖问题成立但属于独立任务，本轮未混入修复。

本轮已修复 4 条闭环问题，前端单测、lint、typecheck、构建与真机回归全部通过。

## 3. 复核后排除的三个疑点

| 疑点 | 结论 | 依据 |
|---|---|---|
| 缺少 `SCHEDULE_EXACT_ALARM` 声明 | **不是缺陷** | `ScheduleCheckScheduler`、`SessionKeepAliveScheduler`、`WidgetAlarmReceiver` 均使用 `setAndAllowWhileIdle`（非精确闹钟），Android 12+ 不会抛 `SecurityException`，也无需运行时授权；代价是分钟级到数十分钟的触发漂移 |
| CSS 全 px 字号不跟随系统 | **不是缺陷** | `MainActivity.java:40-50` 读取系统 `fontScale` 并 `setTextZoom`，clamp 在 0.85–1.5；真实局限是 textZoom 只缩放文字、不缩放容器，系统字号 200% 时上限封顶 150% |
| 路由全量静态 import 浪费体积 | **收益被高估** | 全量懒加载预计只省 8–11 kB gzip、首屏 20–40 ms；只值得拆 `Settings.vue` 单页 |

## 5. 对第二轮结论的三处修正

1. **`keepalive` 登出问题的机制需要修正**。原生 `SsoLoginPlugin.clearSession` 会取消闹钟，`SessionKeepAliveService` 在无 Cookie 时也会取消并返回 `EXPIRED`。因此不是"未登录仍每 30 分钟持续请求"，真实问题是：
   - 开关持久化状态仍为开启；
   - 设置页显示"已开启"；
   - 下次启动会多排一次闹钟；
   - 重新登录后按旧偏好自动恢复保活。
   按同意书"退出登录后自动停止"的承诺，仍属缺陷，定级 P2。本轮修复为退出时显式 `setKeepAlive(false)`，真机验证通过。
2. **通知 ID 碰撞范围收窄**。三个 ID 段为 4100–4599（变更汇总）、7000–7999（变更明细）、8100–8599（成绩），跨类型不会互相覆盖；只有同类型不同记录存在碰撞，概率低。定级 P2。
3. **`npm audit` 数据无法在本机复核**。本机 npm 镜像返回 `404 NOT_IMPLEMENTED`，第二轮报告的 17 条 advisory 需要在官方 registry 重新跑一次再排期，不应直接据此升级依赖。

另：第二轮提出"App 在前台时闹钟走前台广播队列（10s）"这一细节尚未实测确认；无论阈值如何，`goAsync` 不提供长任务保活保证，后台检查的 deadline 收口仍是 P1。

## 10. 结论

第二轮没有发现新的安全缺陷，但补齐了第一轮按目录审查遗漏的跨模块清理与同意闭环。这类问题不涉及漏洞利用，却直接违背用户可见的隐私承诺，属于"低技术难度、高信任成本"的问题。

项目最大风险已从"证书与 SSO"转移到**后台链路、数据清理与同意闭环**。本轮完成 4 条闭环修复并通过真机回归；下一轮建议优先处理崩溃脱敏与无障碍，再进入契约单一化。
