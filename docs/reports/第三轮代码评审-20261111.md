## 1. 摘要

1. 工程水准高于同类个人第三方客户端：网络层有「HTTPS + 主机白名单 + 逐跳重定向校验 + 禁用 URL 凭据」（`HttpPolicy.java:39-64`），Cookie 用 Keystore AES-GCM 加密且 IV 随机随密文同存（`AuthCookieStore.java:42-62`），SSO WebView 有真实证书指纹预检且失败关闭（`SsoLoginActivity.java:86-124`），会话失效收敛到单一出口（`api/index.js:19-28` → `sessionExpiry.js` → `auth.expireSession`），`v-html` 仅用于内置图标常量（`AppIcon.vue:2`、`TabBar.vue:10`），无外部 HTML 注入面。
2. 本轮新增 4 个 P0，均为「判定过宽 / 基准假设未校验」，不是安全防护缺失：
   - 403 与 401 同判为会话失效 → 一次误判清空 Keystore Cookie + 变更历史 + 附件并登出；
   - 退出与会话失效的清理链首步 `clearScheduleChange()` 无保护 → 清理中断、登录态残留；
   - 恢复会话 15s 超时后，迟到的 `sessionExpired` 被吞 → 停留在过期会话且不自愈；
   - 开学日锚点硬编码且未对齐周一 → 锚点非周一的学年，整学期周次与日期区间整体错位。
3. 数据正确性另有 4 个 P1 级静默丢数据路径：消息哈希去重、成绩缺 `totalPage` 只取 100 条、门户分页缺 `totalResult` 只拉 1 页、同一课程多行导致重复 Vue key 渲染错位。
4. 测试体系的主要问题不是覆盖率数字，而是**最复杂的模块被 mock 掉**：`src/stores/academic.js`（513 行、3 个竞态 token、9 个域的三态）在 198 个用例里零执行。

## 4. P0 详述

### P0-1 403 被判为会话失效，触发全量清理本地数据

**位置**：`src/api/zf.js:673-678`（`requestText`），配合 `src/api/index.js:19-28`、`src/stores/auth.js:92-108`。

**现象**：任一业务请求返回 403 时 `failure.sessionExpired = true`，`guarded` 立即 `notifySessionExpired()`，进而 `expireSession()` → `clearLocalSession()`：清 Keystore Cookie、课表快照、变更记录、30 天数据缓存、通知缓存、已下载附件，并跳登录页。

**根因**：本系统真实的未登录路径是「302 到 http 登录页 → 被 HTTPS 策略拦截」（`zf.js:663-668` 已按此判定），403 更可能来自 WAF、模块未开放或权限不足，代码却把它和 401 塞进同一个布尔位。批量请求（`getAllGrades` 串行 N 次、`collectPortalPages` 最多 20 次）更容易触发网关限流 403。

**最小修复**：

```diff
   if (response?.status !== 200) {
     const failure = new Error(`${label}接口返回 ${response?.status ?? '未知状态'}`)
     failure.status = response?.status
-    failure.sessionExpired = response?.status === 401 || response?.status === 403
+    // 403 多为「未开放 / WAF 拦截 / 权限不足」，不是会话失效；判错会清空全部本地数据
+    failure.sessionExpired = response?.status === 401
+    failure.forbidden = response?.status === 403
     throw failure
   }
```

业务层把 `forbidden` 渲染为「教务系统拒绝访问（该模块可能未开放）」，保留本地会话与缓存。

**待确认**：403 在真实网关下的分布（debug 包 + 抓包各验证一次即可闭环）。即便分布很低，这个分支的期望损失（清空 30 天数据 + 强制重登）也大于修复成本。

**回归用例**：`authPost` 返回 403 时断言 `sessionExpired` 未定义、`clearAuthCookies` 未被调用（当前 403 零覆盖）。

### P0-2 退出/失效清理链首步失败即中断，登录态残留

**位置**：`src/stores/auth.js:92-108`（`clearLocalSession` 第一行 `await clearScheduleChange()`）；`src/utils/sessionExpiry.js:8-15`。

**现象**：原生桥 `clearScheduleChange` 抛错时，`clearLocalSession()` 直接 reject：后续 `clearAuthCookies / clearDataCaches / clearPortalCache / clearAttachments` 全部不执行，`user.value` 也不置空。实测 `logout()` 在桥不可用时 `isLoggedIn === true`，加密 Cookie 仍留在本机。由于 `notifySessionExpired()` 的 `try/catch` 接不住异步拒绝，该路径还会抛出 unhandled rejection。

**影响**：换机、退出登录、会话失效三种场景都可能留下上一个账号的会话与缓存数据（隐私面），且用户看到「退出没反应」。

**最小修复**：

```js
// src/stores/auth.js:92
async function clearLocalSession() {
  // 任一步失败都要继续清后面的：原生桥不可用时不能让加密 Cookie 留在本机
  const steps = [
    () => clearScheduleChange(),
    () => clearAuthCookies(),
    () => clearScheduleSnapshot(),
    () => clearDataCaches(),
    () => clearPortalCache(),
    () => Promise.all([clearAuthDownloads(), clearPublicDownloads()])
  ]
  for (const step of steps) {
    try {
      await step()
    } catch (error) {
      // 单步失败不阻断，全部执行完再收敛登录态
    }
  }
  resetAcademicApi()
  user.value = null
  justLoggedIn.value = false
  writePendingFailures(0)
}
```

同时把 `notifySessionExpired` 改成能接住异步拒绝：

```js
// src/utils/sessionExpiry.js:8
export function notifySessionExpired() {
  if (!handler) return
  try {
    Promise.resolve(handler()).catch(() => {})
  } catch (error) {
    // 失效处理失败不能把原始业务错误吞掉
  }
}
```

**回归用例**：`clearScheduleChange` reject 时，断言 `clearAuthCookies` 仍被调用、`auth.isLoggedIn === false`。

### P0-3 恢复超时后迟到的 `sessionExpired` 被吞

**位置**：`src/stores/auth.js:44-62`（`restoreWithTimeout`），配合 `:183-196`（`refreshInBackground`）。

**现象**：15s 超时先 reject 一个 `network` 错误，内层 `restoreSession()` 仍在跑。它稍后若以 `sessionExpired` 拒绝，`reject` 对已 settle 的 promise 无效，**失效信号被静默丢弃**。

**影响**：弱网冷启动或后台静默校验时，用户会长时间停留在已过期的快照数据上，直到下一次主动刷新才被踢回登录页；期间所有请求持续失败。

**最小修复**：

```diff
 function restoreWithTimeout(api) {
+  let timedOut = false
   return new Promise((resolve, reject) => {
     const timer = setTimeout(() => {
+      timedOut = true
       const failure = new Error('恢复登录超时')
       failure.network = true
       reject(failure)
     }, RESTORE_TIMEOUT_MS)
     api.restoreSession().then(
       (profile) => { clearTimeout(timer); resolve(profile) },
       (error) => {
         clearTimeout(timer)
+        // 超时后到达的失效信号必须补发，否则用户会一直停在过期快照上
+        if (timedOut) {
+          if (error?.sessionExpired) notifySessionExpired()
+          return
+        }
         reject(error)
       }
     )
   })
 }
```

需要 `import { notifySessionExpired } from '../utils/sessionExpiry'`。

**回归用例**：fake timers 推进 15.1s 后 reject `sessionExpired`，断言 `clearAuthCookies` 被调用。

### P0-4 开学日锚点未对齐周一，整学期周次与日期区间错位

**位置**：`src/utils/term.js:41-46`（`buildTerm` 硬编码 `YYYY-08-31` / `YYYY+1-02-23` / `YYYY+1-07-01`）、`src/utils/date.js:40-44`（`getWeekNumber` 直接 `floor(days/7)+1`）、`src/views/Schedule.vue:169-204`（`weekRange` / `dayDates` 把锚点当周一加 `(week-1)*7`）。

**现象**：锚点只要不是周一，周次与日期标签就整体错位。实测各学年锚点星期：

| 锚点 | 星期 | 是否错位 |
|---|---|---|
| 2024-08-31 / 2024-02-23 | 周六 / 周五 | 是 |
| 2025-08-31 / 2025-02-23 | 周日 / 周日 | 是 |
| 2026-08-31 / 2026-02-23 | 周一 / 周一 | 否 |
| 2027-02-23 | 周二 | 是 |

实测 `getWeekNumber('2025-08-31', 2025-09-07)` 返回 **2**（同一自然周的周一 09-01 返回 1）。`weekRange` 更直接：2024-08-31（周六）起的「第 1 周」显示 `8/31 - 9/6` 却标注为周一至周日，整学期每周日期都偏 2 天。

**影响**：这是课表主功能的基准——首页「今日课程」、课表「本周」高亮与日期、桌面组件、周次选择器、变更提醒全部共用同一套换算。2026 学年恰好两个锚点都是周一，所以**当期不发作，跨年必复发且用户难以自查**。

**说明**：锚点本身也是假设（学校真实开课日可能不同），但内部不一致是可确定的缺陷——周次换算与日期标签必须使用同一基准，且该基准应是周一。

**最小修复**：

```diff
 export function getWeekNumber(termStart, date = new Date()) {
-  const days = diffDays(termStart, date)
+  const start = toDateOnly(termStart)
+  // 基准回退到所在周周一，避免开学日落在周日/周中造成周次与日期标签错位
+  start.setDate(start.getDate() - ((start.getDay() + 6) % 7))
+  const days = diffDays(start, date)
   if (days < 0) return 1
   return Math.floor(days / 7) + 1
 }
+
+// 供 Schedule.vue 的 weekRange / dayDates 复用，避免两处各算一套
+export function termWeekStart(termStart, week) {
+  const start = toDateOnly(termStart)
+  start.setDate(start.getDate() - ((start.getDay() + 6) % 7) + (week - 1) * 7)
+  return start
+}
```

`Schedule.vue` 的 `weekRange` / `dayDates` 改用 `termWeekStart(currentTerm.startDate, selectedWeek)` 作为第 1 天，不再各自 `new Date(startDate)`。

**验收不变量**（离线可测，不依赖真实开学日）：同一自然周的周一与周日必须返回同一周次；`getWeekNumber('2025-08-31', 2025-09-01) === getWeekNumber('2025-08-31', 2025-09-07)`。

**中期建议**：设置页提供「开学日期校准」，或首次启动时用已下载的校历图人工对照一次。

## 8. 不建议改动（避免过度重构）

- **HttpPolicy / HttpExecutor 的重定向模型**：`HttpUrl.host()` 已完成小写与 IDN 规范化，配合强制 443、禁 URL 凭据、逐跳校验，`//evil.com`、大小写、非标端口、跨域 302 均拦得住。不要为了「更安全」引入 OkHttp `CertificatePinner`。
- **Cookie 加密方案**：IV 随机、随密文同存、Keystore 密钥不可导出、未设 `setUserAuthenticationRequired`。对「后台静默保活」的产品形态这是必要取舍。
- **`parseWeeks` 的双正则 + Set**：区间叠加不会重复计数（Set 兜底），单/双周过滤顺序与 Java 端一致。只需补格式归一，不必改成单次扫描。
- **`<router-view :key="$route.fullPath">`**：代价是切页重挂载，收益是 query 驱动详情页与页面级刷新语义，属合理设计。
- **大列表虚拟滚动 / IndexedDB 迁移**：课表 ≤60 块、成绩数百分组，当前规模用不上。
- **`MainActivity exported=true` + `jiaowu://` 深链**：只能跳白名单页面，id 有 `[A-Za-z0-9_-]{1,64}` 约束，无敏感动作；收紧会失去小组件能力。
- **`v-html` 的两处使用**：数据源是内置图标常量，无需引入 sanitizer。
