## 1. 摘要

本次审查对前端（Vue 3 + Pinia + Capacitor）、Android 原生壳、后台提醒、桌面组件与测试体系做了全量检查，并对关键结论逐条复核源码，避免把误报带入修复。

核心结论：

1. 工程质量基线高于同规模个人项目：181 个前端单测与 16 个 Android 测试类全通过，lint 与 typecheck 通过，release 强制签名、R8、白名单与重定向逐跳校验均已落地。
2. 存在 **2 个 P0 安全问题**，均已在本次修复：
   - 统一认证证书指纹校验实际从未在正常 HTTPS 链路执行；
   - Keystore 加密失败时静默降级为明文落盘。
3. 存在**一类已发生的双端语义漂移**：JS 与 Java 各维护一份节次表与消息 ID 规则，已出现实际不一致，且后台路径会自我维持错误状态。
4. 主要结构性风险集中于**双端重复实现缺少单一契约**，而不是散落的编码错误。因此改进优先级应为"先止血、再统一契约、最后重构"。

## 6. 对初审结论的三处修正

审查报告本身存在三处表述需要修正，已并入本报告结论：

1. **SSO 证书固定的机制比"可能被绕过"更明确**：`network_security_config.xml` 中的 SPKI pin 只约束走平台网络栈的请求，**WebView 不执行 NSC 证书固定**；代码里的指纹比对又只在 SSL 错误回调触发。两层防线，一层不覆盖 WebView，一层在正常链路不执行。问题不是"可能失效"，而是**承诺的安全能力从未生效**。
2. **节次漂移的影响面要收窄**：只命中"升级前已有基线、且后台检查先于下一次前台对账"的安装，不是全体用户。链路为：后台读基线（`ScheduleChangeService.java:242`）→ 取不到 13–15 节（`ScheduleChangeEngine.java:53`）→ 按 23:59 兜底（`DateUtils.java:96-112`）→ 12 项表写回基线。症状是"已结束的课仍在提醒"，不损坏数据，维持 P1。
3. **缓存 TTL 不短路请求不是缺陷**：README 只承诺"离线回退 + 过期标注"，当前行为符合承诺；成绩 20 页串行全量拉取属于独立性能问题，应单列 P2，不应算作功能缺失。

另：初审中"后台广播 10s ANR"的说法已被修正为 **60s**（前台广播才是 10s），26s 并非必然超时。

## 7. 本次已实施修复

### 7.1 SEC-02：LocalCipher 失败关闭

改动：

- `LocalCipher.seal()` 加密异常时返回 `null`，不再返回明文。
- 5 个调用方全部改为"加密失败即跳过写盘、保留旧数据"，避免 `putString(key, null)` 误删旧值：
  - `ScheduleChangeStore`（课表基线、变更记录）
  - `GradeAlertStore`（成绩基线）
  - `PortalAlertStore`（提醒学号）
  - `WidgetStore`（组件 payload）

影响与取舍：

- Keystore 不可用时，组件/基线的本次更新会被放弃，可能短暂显示旧数据；这是有意选择——**不写优于写明文**。
- 读取路径保持兼容：历史明文仍可按原样读取，下一次成功加密后自动升级。

### 7.2 SEC-01：SSO 加载前证书预检

改动：

- 加载登录页前，在后台线程用 OkHttp 对 `authserver` 发起一次 HEAD 预检，通过后才加载 WebView。
- 预检使用**只认内置 SHA-256 指纹的自定义 TrustManager**：指纹不一致直接终止登录；不依赖系统 CA 是否信任。
- 失败分两类提示：
  - 证书问题：显示"证书校验失败"，说明可能被劫持/证书轮换/系统时间异常；
  - 网络问题：显示"无法连接统一认证"，提供"重试 / 取消"。
- 保留原 `onReceivedSslError` 分支作为兜底（覆盖证书过期但指纹一致的场景）。

为什么不用"系统校验 + 指纹"：

- 实测服务器证书由 Let's Encrypt 签发，而 minSdk 23 的 Android 6 系统信任库不包含对应根证书。
- 若预检要求系统 CA 通过，会把 Android 6 用户误拦；只认指纹既保持固定语义，又消除版本差异。
- 预检失败即失败关闭，不会加载任何未固定的登录页。

## 9. 残留风险与边界

修复后仍需明确三点：

1. **预检是时间点校验**：通过后加载 WebView，后续导航仍依赖系统信任链，指纹不会逐请求复核。要彻底消除该窗口，需要把 CAS 登录整体改为 OkHttp 承载，或在 WebView 侧做拦截式校验。
2. **证书轮换仍需发版**：指纹固定意味着认证服务器换证后必须更新代码与 NSC 配置并重新发版，这是既定策略，不是缺陷。
3. **加密失败不落盘会丢失一次更新**：这是有意的可用性代价，需在诊断日志中可观察（已通过 `ChangeDebug` 记录，仅 debug 包输出）。

## 10. 三个悬而未决问题的结论

| 问题 | 结论 |
|---|---|
| 13–15 节课是否真实存在 | **问题不成立**。App 自身允许用户配置 6–15 节，Java 必须覆盖 15 节。修法是单一数据源，不是判断"学校是否真的排到 15 节" |
| 缓存目标是"少发请求"还是"断网可看" | 按 README 承诺，当前实现"断网可看 + 过期标注"是正确行为，不算缺陷；若要"少发请求"，属于产品变更，单独立项 |
| 是否为 `zfjw` 增加证书 pin | **暂不增加**。它走 OkHttp + 强制 HTTPS + 主机白名单，攻击面小于 WebView；而 pin 会把每次证书轮换变成强制发版，收益不对称。先把 `authserver` 的固定真正生效 |

## 11. 建议路线

### 阶段 1：止血（全部为小改动、低风险）

1. `GradeFetcher` 补会话失效语义，复用 `notifySessionExpired`。
2. `clearLocalSession` 增加下载缓存清理（附件与正文图）。
3. SSO 登录增加超时出口，避免 Promise 永久悬挂。
4. 后台检查统一 deadline：`join(2000)` + 后台 `MAX_PAGES=1` + `pending.finish()` 放入 `finally`。
5. 节次表改为单一数据源 + parity 测试（修"15 vs 12"与死代码 `readSectionTimes(Context)`）。

### 阶段 2：契约单一化

抽 `src/shared/{hosts, keys, schedule-defaults, id-fields}`，Java 侧生成或读取同一份数据，CI 增加 diff/parity 断言；补 `src/native/*.d.ts` 与统一错误结构。此阶段不改运行时行为，却能消灭大部分 P1。

### 阶段 3：结构重构（延后）

`zf.js` 切片、store 资源工厂、拆分 `Home` / `Settings`。当前阶段（功能跑通 + 真机验证）收益低于风险，等契约层落地后再做。

### 明确不做

- 不为 `zfjw` 增加 pin；
- 不在本轮做 4–6 人日的结构重构；
- 不为"TTL 不短路"改运行时行为（仅必要时澄清文档）。

---

## 12. 结论

本次审查验证了项目的基本工程质量，也暴露了两个"承诺与实现不一致"的安全问题。两者均已修复并通过真机冒烟；其中证书固定改为加载前正向校验，加密落盘改为失败关闭。

项目仍处在一个可控但不应拖延的阶段：**真正的风险不是单点 bug，而是 JS 与 Java 各自实现同一规则却没有契约**。先完成阶段 1 与阶段 2，可以最小的代价把 3 / 5 的成熟度提升到可长期维护的水平。
